# 撰写与重构技术书籍指南

技术书籍的目录是读者获取信息、评估书籍价值的“骨架”。目录的核心目标是**快速导航**和**引发阅读兴趣**，而不是作为详细的说明书。

在编写或审查技术书籍目录时，请严格遵循以下原则：

## 1. 定位：目录是导航，不是说明书
- **精简文字**：删除所有冒号（`：`）后用于解释或说明的长句。具体的原理解释、背景介绍应放在正文中，而不是目录里。
- **提升扫视效率**：目录需要保持清爽。消除“密密麻麻”的观感，让读者一眼就能看清整个章节的骨架和逻辑递进关系。

## 2. 命名风格：中性、专业与探讨性
- **拒绝“结论式”标题**：不要在标题中直接给出答案（例如避免使用“为什么抛弃递归”或“隐形的成本杀手”）。结论式标题缺乏探讨性，显得内容单薄（“一眼看到底”），会降低读者的探索欲。
- **使用“探讨性”短语**：改用中性、客观的专业术语组合。
  - ❌ 错误（结论/口语化）：`为什么抛弃递归？`
  - ✅ 正确（中性/专业化）：`递归的局限性`
  - ❌ 错误（口语/夸张）：`隐形的成本杀手：Cache TTL 探测`
  - ✅ 正确（中性/客观）：`缓存生存时间探测`

## 3. 英文缩写与专业词汇控制
- **克制使用英文解释**：绝对不要在标题中放置基础的英文翻译或解释。
- **常见无歧义词汇**：如 Agent, Token, CLI, ReAct 等，可以直接使用，无需翻译或加括号解释。
- **生僻或有歧义词汇**：在目录中尽量使用精准的中文提炼，将其英文原词及解释放在**正文第一次出现的地方**（全书仅解释一次）。

## 4. 结构与层级
- **紧凑而逻辑清晰**：通过精准的名词短语来构建层级。每一个小节的标题都应该是对该节内容的**高度抽象提炼**。
- **字数控制**：小节标题尽量控制在 5-15 个中文字符以内，做到多一字多余，少一字意不达。

## 示例对比 (Examples)

### ❌ 修改前的糟糕范例
```markdown
第 2 章：解构 Claude Code —— 从逆向工程看系统级 Agent 架构
2.1 核心循环体（The Core Loop）：打破递归魔咒的状态机
2.1.1 为什么抛弃递归？
2.2 Coordinator 模式：多智能体间的“总指挥”艺术
2.5.2 多重竞跑机制（Multi-Racer Resolution）
2.10.1 隐形的成本杀手：Cache TTL（生存时间）探测
```

### ✅ 修改后的优秀范例
```markdown
第 2 章：解构 Claude Code 的架构设计
2.1 核心循环体与状态机
2.1.1 递归的局限性
2.2 Coordinator 调度模式
2.5.2 多重竞跑机制
2.10.1 缓存生存时间探测
```

**核心自检清单 (Checklist):**
- [ ] 标题中是否包含不必要的英文单词或括号解释？
- [ ] 标题是否太长，包含了解释性的说明语句？
- [ ] 标题是否泄露了结论，导致失去了探讨的深度？
- [ ] 整体结构是否足够干净，能够让读者在一秒钟内扫视出章节骨架？

## 5. 正文写作手法（出版界最佳实践）

在编写技术书籍正文（特别是偏向实战与底层架构的硬核专著）时，为了消除干瘪的“PPT式汇报感”或“说明书感”，应借鉴顶级技术出版物（如 O'Reilly）的以下写作技巧：

### 5.1 概念隐喻（Metaphorical Mapping）
- **核心**：技术书籍最怕干瘪。最好的技术书一定擅长用生活中的物理实体来映射代码里的抽象概念。
- **示例**：把 `BashTool` 的防线比作“银行的防弹玻璃柜台”；解释 `Event Bus` 时说“就像是公司里的布告栏，而不是单线打电话”。

### 5.2 “为什么不”驱动法（Negative Motivation）
- **核心**：比起一上来就写正确的代码，读者更喜欢看“错误是怎么发生的”。
- **写作公式**：抛出一个大家都以为对的常识方案 -> 演示它在真实环境里是如何崩溃的 -> 解释背后的深刻原理 -> 给出正确的架构代码。

### 5.3 代码的“呼吸感”排版（Code Breathing）
- **核心**：长达百行的连片代码是读者的噩梦。
- **排版技巧**：
  - **代码标注 (Callouts)**：不把大段解释写在代码注释里，而是在代码块下方用 `1. 2. 3.` 对应讲解。
  - **剥离样板代码**：只贴出跟当前小节强相关的核心逻辑。
  - **对比法 (Diff-style)**：当从基础版向高阶版重构时，直接指出“这几行是我们新加的防线”。

### 5.4 情境代入式标题（Contextual Headings）
- **核心**：传统的论文式子标题很死板。现代技术书籍更喜欢“解决问题式”的标题。
- **示例**：将 `统一凭据与路由` 升级为 `统一凭据与路由：终结“多模型配置灾难”`，让目录自带钩子，吸引读者阅读。

### 5.5 黄金路径原则（Golden Path / Happy Path First）
- **核心**：在介绍一个极其复杂的架构时，不要一上来就罗列所有的异常分支、错误捕获和边界条件。
- **递进设计**：先写出一条完全没有任何错误处理的“黄金路径”，等读者理解了主干，再开启一个小节（如：“如果在这个过程中网络断了怎么办？”）来自然引入降级或防御性编程。

### 5.6 前后向指针（Forward and Backward Pointers）
- **核心**：避免在文中硬编码章节号（如“见第 10 章”），避免因大纲调整而导致满盘皆错。
- **流动表达**：
  - **回顾 (后向指针)**：“正如我们在前文探讨 AST 沙箱时所见……”
  - **预告 (前向指针)**：“这个痛点，我们将通过后续实战章节的 Coordinator 模式彻底解决……”

### 5.7 读者护栏（Guardrails & Pitfalls）
- **核心**：在教授最佳实践的同时，立起“护栏”，明确告诉读者什么**绝对不能做**。
- **表现形式**：通常用 `⚠️ 警告`、`💡 最佳实践` 或 `💣 避坑指南` 等提示框来标识。

### 5.8 用词密度管控（Diction Density Control）

技术书籍最隐蔽的质量问题不是单个用词不当，而是**同一句式/词汇被高频复用**导致文风死板。以下规则基于对标《凤凰架构》（周志明）、《数学之美》（吴军）、CS:APP 中译本等顶尖技术书籍的用词密度总结而成。

**密度基准**（以 15-20 万字全书为参照）：

| 词/句式 | 健康上限 | 常见病态值 | 说明 |
|---------|---------|-----------|------|
| “而非” | 30-40 次 | 100+ | 最常见的万能转折词滥用 |
| “本质(上/是/就是)” | 8-12 次 | 20+ | 每个概念都“本质”则无一概念有本质 |
| “正是” | 12-18 次 | 30+ | 强调收束词，频繁使用则失去力度 |
| “其核心是” | 5-8 次 | 15+ | 与“本质”同类的过度揭示 |

**“而非”的替换策略**（从 100+ 砍到 30-40）：

| 场景 | 滥用写法 | 替换方案 |
|------|---------|---------|
| 技术对比 | “用 Channel 而非 Mutex” | “用 Channel，不用 Mutex” |
| 设计拉择 | “返回副本而非指针” | “返回副本——指针会带来竞态”（说原因） |
| 概念澄清 | “是启发式调优而非严格 Hill Climbing” | “属于启发式调优，不是严格的 Hill Climbing” |
| 否定陈述 | “应在读取边界做视图，而非维护独立表” | “在读取边界做视图就够了，不必维护独立表” |

**保留“而非”的场景**：精确的 API 语义辨析、类型系统的形式化对比、一句话内的强对比收束。

**“本质”的替换策略**（从 20+ 砍到 10 以内）：

| 滥用写法 | 替换方案 |
|---------|---------|
| “本质上是一个内存数组” | “说白了就是一个内存数组” |
| “本质是把 continuation 从隐式提升为显式” | “目的是把 continuation 从隐式变成显式” |
| “IO-bound 并行的本质是重叠等待时间” | “IO-bound 并行的关键在于重叠等待时间” |

只在**全章最核心的一两个概念揭示**处保留“本质”，其余用“其实”“说白了”“关键在于”“归根结底”或直接陈述。

**“正是”的替换策略**（从 30+ 砍到 15 左右）：

“正是”是论证链的收束词，只应出现在“揭开谜底”的位置。当普通因果连接也用“正是”时，读起来像在反复敲桌子。替换为“就是”“便是”或直接去掉。

### 5.9 章节自指消除（Eliminating Meta-Narration）

在正文叙事段落中反复说“本章将……”“本节我们……”“在本章中……”称为**章节自指**（meta-narration）。读者已经在读该章，不需要被反复提醒。

**必须消除的场景**：
- 章/节开头的概述句：“本章探讨如何……” → “接下来探讨如何……” / “下面……”
- 过渡句：“本章用 Go 语言将该机制复现” → “下面用 Go 将该机制复现”
- 总结句：“读至本章，主线已走完” → “到这里，主线已走完”

**可以保留的场景**：
- 跨章实现边界说明：“本章的 RunLoop 尚未实现 HITL 挂起”（告诉读者“这里故意没做完”）
- 技术范围声明：“本章的实现重心落在 Logs + Traces + Cost 三条线上”
- 结构化导读框内的体例约定（“本章核心问题”“读完本章你能回答”）

**替换词库**（避免新的重复模式，交替使用）：
- “本章” → “接下来” / “下面” / “我们” / 直接省略
- “本节” → “这一节” / “下面” / 直接省略
- “读至本章” → “到这里” / “至此”

### 5.10 标点密度纪律（Punctuation Discipline）

**破折号“——”**：中文破折号是“行文中的插入解释”，本身没错，但密集使用会产生特殊的阅读节奏——每句话读到一半被拦下补充——然后再回到主句——注意力被反复打断。这是 AI 辅助写作的典型痕迹。

密度基准：每章 **10-20 次**为健康区间（15 万字全书约 150-250 次）。超过每章 40 次即需审视。

**替换策略**：
- 短补充 → 融入句子或用逗号断开
- 术语解释 → 用括号 `（）`
- 长补充 → 另起一句
- “A——B——C”夹心饼结构 → 必须拆开，读者无法同时追踪两层插入

### 5.11 加粗与强调纪律（Emphasis Discipline）

当半页都在加粗时，**加粗等于没加粗**。

**加粗只用于两类场景**：
1. **术语首次定义**：该术语在全书第一次出现并被正式解释时加粗
2. **关键结论**：一个段落论证后的核心判断句

**不应加粗的场景**：
- 解释性文字、补充说明
- 已经出现过的术语的后续使用
- 代码中的变量名、函数名（应该用行内代码 `` ` `` 标记）
- 普通的并列名词

密度基准：每千字正文（不含代码块）加粗不超过 **3-5 处**。单章超过 80 处加粗即需审视。

### 5.12 审稿笔记零残留（No Review Notes in Manuscript）

在为读者撰写与出版的书稿中，所有技术说明必须使用面向读者的、连贯的正文语言呈现；禁止将审稿笔记、TODO、内部讨论、审阅意见或实现跟踪直接留在正文或示例代码注释中。请将以下规则纳入写作检查清单：

- 规则：写书时不做审稿笔记。任何对实现变更、比较或借鉴的说明都应改写为中性、面向读者的正文（解释为何采用该方案、备选方案与权衡），不得保留“审稿备注/实施注记”类文字。
  - 禁止示例（不得出现在正文或代码注释中）：
    - “参考 beauty 做了调整” / “已按 reviewer 建议改动”
    - “TODO: 后续再补充实现细节” / “待与某某讨论后再改”
    - “审稿意见：这里应该改成…”
  - 允许示例（应改写为此类形式）：
    - “为保证可恢复性，本设计将审批从工具执行中剥离，改为循环级的原子暂停与续跑，以便把待批项写入 checkpoint 并支持跨请求恢复。”
    - “权衡：将审批放在循环层避免了无法序列化的阻塞 goroutine，但代价是需要在 Run/Continue 接口上增加恢复语义。”
  - 文本模板（便于把审稿笔记改写为正文）：
    - 审稿笔记 → 正文表述示例：
      - “（审稿）X 不合适” → “为保证 Y，选择方案 A，而非方案 B，原因是 …”
      - “(待确认) 是否用 Z？” → “可选方案：使用 Z 可带来 …；但同时会引入 …，因此本书采用 …”

简短说明：此规则保证书稿面向读者、叙述连贯、可复现；审稿记录与开发备忘应另存为作者工作记录或附录，不应进入最终正文或示例代码注释。

## 附录 A：出版社稿件规范

以下规范属于出版行业强制性要求，优先级高于风格建议。

### A.1 交稿"五衔接、六统一、七对应"

交稿时应做到：

**五个衔接**：章、节的序号，表号，图号，公式号，页码要衔接、连续，不应有重号或跳号。

**六个统一**：格式、层次、名词术语、符号、代号、计量单位要统一。

**七个对应**：目录与正文标题、标题与内容、正文与插图、正文与表格、脚注与被注释内容、图注代号与图注，以及书中内容前后对应。

### A.2 层次编号

- 层次不宜过多，各层次标题末尾**不加标点**。
- 科技图书采用《科技文献的章节编号方法》CY/T 35—2001 标准：章 `1`、节 `1.1`、小节 `1.1.1`、条 `1.`、款 `1)`、项 `(1)`、段 `①`。
- 在正文中引用时，`1.1`、`1.1.1` 和 `1.1.1.1` 均称为"节"，不称为"小节"。例如"参见 1.1.1 节"。
- 全书以章为基本划分单元，即使设有篇的层次，全书章号仍自始至终连续。

### A.3 名词术语

- 科技名词术语应全书统一，采用"全国自然科学名词审定委员会"公布的名词。
- 新名词或新译名首次出现时，应酌情加注释或注出相应的外文名称。
- 外国人名定名的术语不要将英、汉文混用（如"傅里叶变换"不要写成"Fourier 变换"）。

### A.4 标点符号要点

| 符号 | 规则 |
|------|------|
| 顿号与逗号 | 外文、阿拉伯数之间的并列用逗号不用顿号（如 `a，b`）；不同层次的并列应以顿号、逗号区别 |
| 分号 | 分号之间不能有句号；被分号隔开的各分句中，至少应当有一组内部有逗号，否则不用分号 |
| 省略号 | `…`（3 点）用于外文/数字省略；`……`（6 点）用于汉语省略 |
| 冒号 | 一个句子里不能出现两重冒号 |
| 引号 | 独立引用时句末标点在引号内；引语作为句子组成部分时句末标点在引号外 |
| 括号 | 注释前面词语时：`×××（×××）。`；注释全句时：`×××。（×××。）` |
| 书名号 | 只限用于中文，其他文种应遵从该文种习惯 |

### A.5 数字用法

**必须使用阿拉伯数字的场景**：
- 统计表中的数值（正负整数、小数、百分比、分数、比例）
- 公历世纪、年代、年、月、日、时、分、秒（年份不简写，如 1996 年不写成 96 年）
- 物理量和计数量量值（如 `500 g`、`35.6 m²`）
- 部队番号、文件编号、证件号码和其他序号

**必须使用汉字的场景**：
- 定型词、成语、惯用语中作为语素的数字（如"一方面""四氧化三铁""五四运动"）
- 相邻两个数字并列表示概数（如"三四米""五六天"，中间**不加顿号**）
- 带"几"字的约数（如"几百年""十几天"）
- 不在统计语境中的整数一至十（如"一个人""三种产品"）

**数值范围表示**：
- `10%～20%`，不写成 `10～20%`
- `2×10³～6×10³` 或 `(2～6)×10³`，不写成 `2～6×10³`
- 纯小数必须写出小数点前的 `0`（如 `0.52`，不写成 `.52`）

### A.6 插表规范

- 表号按章编排：`表1-1` 表示第 1 章第 1 个表。
- 表题末**不加标点**，置于表的**上方**居中。
- 插表的表号应在正文中**先引后出**（先见文后见表）。
- 表头中量与单位间用斜线分开（如 `密度/(kg/m³)`），避免二重斜线。

### A.7 插图规范

- 图号按章编排：`图1-1` 表示第 1 章第 1 个图。
- 图题末**不加标点**，置于图的**下方**居中。
- 分图用 `(a)`、`(b)` 编号，分图号、分图题置于分图下方居中。
- 标注内容较多时，用阿拉伯数字按顺时针方向顺序编号。

### A.8 计算机图书术语规范

**鼠标操作**：
- 单击：按一下鼠标左键。**不用**"点击""点取""点"。
- 右击：按一下鼠标右键。
- 双击：连续快按两下鼠标左键。
- 拖动：按下鼠标左键同时移动鼠标。

**键盘操作**：
- "按某某键"：输入单个键或组合键。不用"键入某某键"。
- "键入某某"或"输入某某"：在文本框中输入连续性文字。
- 键盘上的称为"键"，屏幕界面上的称为"按钮"。

**组合键**：用 `+` 连接，书写顺序为 Shift、Ctrl、Alt（如 `Shift+Ctrl+Alt+A`）。键名不加引号或方括号。

**菜单连写**：连续操作菜单用 `→` 或 `|` 连接（如 `【文件】→【另存为】`），全书统一。

### A.9 注释格式

- 尽量在文内用括号注释。
- 不随文列出的注释采用脚注：正文中需加注处的右上角加注码 ①，本页末画横线隔开写注文。
- 脚注编号以本页为限，另页从 ① 重新计起。

### A.10 参考文献

采用"顺序编码制"或"著者-出版年制"，全书格式统一。

**顺序编码制**：按在正文中出现的先后用阿拉伯数字连续编码，加方括号放在加注处右上角（如 `爱因斯坦[2]`）。文献为叙述代名词时与正文并排（如 `证明见文献[4～6]`）。

## 附录 B：稿件规范补充（图表、标题与正文一致性）
为保证技术书稿的专业性与可读性，补充三条具体写作与排版规范，供作者与编辑严格遵守：

1. 图表规范（先文后图、按章编号、名称一致）
   - 先引后用：正文中必须先出现对图/表的引用文字（例如“如图1-1所示”或“见表2-3”），随后才能在合适位置放置对应图表。避免文中未提及即放图表的情况。  
   - 按章编号：图、表编号采用“章编号-序号”格式（例如第1章第一张图为“图1-1”，第2章第一张表为“表2-1”）。编号应自洽且连续。  
   - 名称一致：图题（图下方）与表题（表上方）使用的措辞，须与正文中引用时的描述完全一致（逐字匹配），以避免读者混淆。

2. 标题衔接（禁止“标题挨标题”、必须有过渡段）
   - 禁止断层：在任意相邻层级标题之间（如一级→二级、二级→三级）不得直接相连。必须插入一段承上启下的过渡段，说明本节目的与结构，概述主要观点或要解决的问题。  
   - 过渡段功能：简短（1–3 段）地说明本节与前后节的逻辑关系、核心目标和阅读预期，帮助读者建立章节内外的认知桥梁。

3. 正文与标题呼应（关键词锚定、防止跑题）
   - 首尾呼应：每一节的首段（开头一句）与尾段（结尾一句）应明确包含并呼应本节标题的关键词，形成闭环式的逻辑聚焦。  
   - 逻辑聚焦：正文论述应严格围绕标题核心展开，避免在本节中引入与标题无关的大篇幅延伸话题；若确需扩展，应另起小节并以小节标题予以标示。

4. 层级标题匹配（大标题与小标题同轴）
   - **问题—方面结构**：上级标题定义一个问题（或一个明确论域）；子级标题必须沿着上级标题的关键字，各自分析该问题的一个方面。
   - **主线一致**：子标题集合必须符合上级标题的主线。若上级标题承诺了 N 个相关方面（或隐含 N 个维度），子标题一般也应对齐为 N 个子问题，数量与语义都要兜得住上级承诺。
   - **允许的延展**：在主线子问题之外，顶多可有少量横向对比、案例、旁证等延展小节；这些延展不得喧宾夺主，也不能把主线拆散成另一条叙事。
   - **不匹配判据**（出现任一即需改标题或调结构）：
     - 子标题讨论的对象已跳出上级关键字所圈定的论域；
     - 上级说了三方面，子级却写成无关的五六条清单，或漏掉承诺过的方面；
     - 子标题之间彼此平行，但合起来无法回答上级标题提出的问题。

以上四条为投稿与编校的强制性规范（非风格建议）。请在后续稿件提交与校对阶段，逐条校验并在校稿清单中打勾确认。

## 6. 全书结构治理

### 6.1 独子标题必合并
若某个父标题下只有**一个**子标题，说明分级冗余。应将子标题内容合并入父标题，消除空壳层级。
- ❌ `## 7.5 并行加速器` → `### 7.5.1 调度与熔断`（唯一子标题）
- ✅ 去掉 `### 7.5.1`，内容直接归入 `## 7.5`

### 6.2 并行章节体量均衡
同一"篇"内地位对等的章节（如同属"分析篇"的第 2、3、4 章），二级标题数量不宜相差 2 倍以上。严重失衡意味着某章过度膨胀或另一章内容不足，应通过合并或拆分恢复比例。

### 6.3 跨篇桥接节
当全书由"分析篇"过渡到"实现篇"时，交界处需要一个**提炼性的过渡节**，将前篇解构中提取的架构模式、设计权衡显式映射到后篇的实现章节。没有这一节，读者会感到"突然换了本书"。

### 6.4 全书末节收束
最后一章的最后一节不应打开全新话题。展望型内容可以有，但**末句必须回扣全书核心概念**，给出"第一性原理不变"式的收束，而非以开放问题或新话题结尾。

## 7. 标题深层规则

### 7.1 章标题关键词着陆
如果章标题承诺了某个概念（如"洋葱模型"），至少一个二级或三级标题必须包含该关键词。否则读者在目录中找不到着陆点，产生"标题与内容脱节"的印象。

### 7.2 同章标题风格一致
同一章内的二级标题风格不能两极分化（如一半学术中性、一半口语营销）。不同章之间允许微调风格差异，但**同章内必须统一**。

### 7.3 "进阶展望"是反模式
`进阶展望：XXX` 是常见的懒惰标题——冒号前是套话，冒号后才是真正主题。应直接使用技术主题作为标题。
- ❌ `进阶展望：从单机状态机到分布式持久化执行`
- ✅ `分布式持久化执行`

### 7.4 标题措辞影响深度感知
同样的 200 行深度内容，标题叫"进阶展望"和叫"工程选型"，读者感知的分量完全不同。标题应准确反映内容的实际深度，避免"展望/延伸/补充"等词无意中贬低已有的实质内容。

## 8. 内容组织策略

### 8.1 散布内容的枢纽节
当一个概念（如"成本工程"）的实现散布在 4-5 个章节时，应在最相关的章节中添加一个"全景"子节，用显式的章节交叉引用将散布的策略串成完整链路。与§5.6"前后向指针"的区别：指针是单点引用，枢纽节是**结构化的全景聚合**。

### 8.2 协议/标准类内容的深度阈值
涉及行业协议（如 MCP、A2A）时，仅做"定位对比表"不够。至少需补充**传输机制**（如 JSON-RPC / stdio / SSE）和**核心实体的生命周期状态机**，才能达到技术著作的可信度阈值。纯概览级对比会被读者认为"一笔带过"。

### 编校自检四查（审稿必做）

写完或改完一章后，按下列顺序做一遍机械检查；发现问题立刻改，不要留到终校。

1. **查图表**
   - 全局搜索「图」「表」字样。
   - 确认每一个图表都在正文中被**提前**提到（先引后用）。
   - 确认图表编号与所在章节对得上（如第 3 章只能出现「图3-x / 表3-x」）。

2. **查标题衔接**
   - 浏览目录或正文，检查是否出现一连串标题连着排、中间一行正文都没有的情况。
   - 若有，立刻补齐过渡引导语（禁止「标题挨标题」）。

3. **查关键词**
   - 看一眼某个小结的标题，再看一眼该小结正文的第一段。
   - 正文第一段里必须包含标题里的核心词；若没有，改写首段或调整标题，使二者锚定一致。

4. **查层级匹配（大标题 ↔ 小标题）**
   - 抽出每一级上级标题的关键字与它所定义的问题。
   - 逐条核对子标题：是否各自覆盖该问题的一个方面，且仍落在上级关键字的主线上。
   - 若上级承诺了若干方面，核对子标题数量与语义是否对齐；延展性小节（对比、案例）是否明显少于主线、且不抢戏。
   - 发现不匹配时：优先改子标题以贴合上级，或收窄/改写上级标题使其真实覆盖子级内容——二者必须同轴，不能各说各话。
